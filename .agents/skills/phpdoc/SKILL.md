# PHPDoc моделей и сервисов

Модели в `app/Models/` и сервисы во всех подкаталогах `app/Services/` должны иметь актуальную документацию PHPDoc на русском языке. Имена классов, методов и PHPDoc-теги сохранять в исходном виде.

## Область работы

При создании или изменении модели либо сервиса документировать класс и все объявленные в нём методы, включая связи, scopes и непубличные методы. Для отдельного запроса на документацию охватывать указанные пользователем классы; при запросе на все модели и сервисы проверять оба каталога рекурсивно. Не расширять обычную правку на остальные классы проекта.

Перед написанием комментариев читать реализацию, а для моделей — соответствующие миграции и casts. При описании бизнес-правил учитывать вызывающий код, `app/Observers/PaymentObserver.php`, `config/referral.php` и существующие тесты по мере необходимости. Комментарии должны отражать фактическое поведение. Если оно расходится с требованиями, сообщить об этом отдельно; задача на PHPDoc сама по себе не разрешает менять бизнес-логику.

## Модели

- DocBlock класса объясняет назначение сущности и существенные ограничения, подтверждённые кодом или схемой.
- Описывать атрибуты через `@property` с типами с учётом casts, nullable-полей и временных меток. Не выводить тип только из названия столбца или `$fillable`.
- Описывать динамические свойства связей через `@property-read`: коллекция для связи «многие», модель с обоснованной nullable-семантикой для одиночной связи.
- Для методов связей указывать назначение и уточнённый `@return`, например `HasMany<Payment, $this>` или `BelongsTo<Master, $this>`. Использовать существующие импорты или полные имена классов; число параметров сверять с объявлениями установленной версии Laravel при сомнениях.
- Для scopes описывать реальные условия фильтрации и уточнять `Builder` через `@param Builder<Payment> $query` и `@return Builder<Payment>` с соответствующей моделью.
- Не приписывать scope условия похожего вспомогательного метода: фильтр по типу платежа сам по себе не гарантирует положительную сумму.

## Сервисы и методы

- DocBlock сервиса объясняет его ответственность; DocBlock метода — результат и значимые условия выполнения.
- Описывать смысл параметров, единицы сумм, источник настроек и правила округления, когда они подтверждены реализацией. Если единицы измерения не установлены, не придумывать рубли или копейки.
- Указывать смысл `null`, поведение при повторном вызове, побочные эффекты и обработку недопустимых входных данных, если они есть.
- Добавлять `@param` и `@return`, когда они уточняют смысл, nullable-результат, generics или структуру массивов. Не дублировать очевидные нативные типы тегами без полезного пояснения.
- Добавлять `@throws` для подтверждённых исключений, существенных для контракта метода; не перечислять предположительные ошибки инфраструктуры.
- Разделять создание привязки и начисление вознаграждения согласно реальным ответственностям сервиса и observer. Не утверждать, что метод регистрации сам начисляет выплату, если он лишь создаёт или возвращает привязку.
- Сохранять фактическую формулу `ReferralService::rewardAmount()` и условия допуска платежей в `PaymentObserver`; не исправлять вычисления в рамках документационной правки.

## Проверка результата

Сопоставить описания с кодом: фильтры scopes, возвраты, повторные вызовы, nullable-типы и побочные эффекты. Проверить diff: при задаче только на документацию изменения должны ограничиваться PHPDoc. Выполнить `php -l` для изменённых PHP-файлов. Не устанавливать генераторы, анализаторы или новые зависимости только ради комментариев. Если менялась логика по отдельному поручению пользователя, выполнить соответствующие тесты проекта.
