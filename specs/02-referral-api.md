# 02. Контракт и реализация реферального API

## Цель

После этапа 01 реализовать три маршрута из README через `app/Http/Controllers/ReferralController.php`. Маршруты уже объявлены в `routes/api.php`, но контроллер отсутствует. Используй `ReferralService` для регистрации; не дублируй правила начисления в контроллере.

## Идентификация и ошибки

`X-Master-Id` — заглушка идентификации. Бери модель из `request()->attributes->get('current_master')`. Для реферальных маршрутов отсутствие заголовка, нецелочисленное/неположительное значение и неизвестный мастер дают HTTP 401 с JSON `{"message":"Current master not found."}`. Проверяй формат до запроса в БД.

`GET /api/ping` остаётся публичным и возвращает `{"ok":true}`. Страницы и выгрузки документации также не требуют этого заголовка. Ошибки реферального API должны быть JSON даже без `Accept: application/json`; не включай глобальное требование заголовка для всех маршрутов.

## POST /api/referrals/attach

Тело: `{"code":"MASHA10"}`. `code` — обязательная непустая строка до 255 символов; не вводи автоматическое изменение регистра. Идентификатор приглашённого берётся только из заголовка, поля тела не могут его подменять.

- Первая привязка: HTTP 201, `created: true`.
- Повтор с допустимым кодом: HTTP 200, `created: false`, вернуть существующую привязку без изменения реферера. Это относится и к другому существующему чужому коду.
- Неизвестный или собственный код: HTTP 422, в том числе если привязка уже существует. Сохрани порядок проверки кодов в сервисе.
- Невалидное тело: HTTP 422. Для ошибок кода используй Laravel-совместимые поля `message` и `errors.code` (массив сообщений).

Успешный ответ:

```json
{
  "created": true,
  "data": {
    "id": 5,
    "referrer_master_id": 1,
    "referred_master_id": 2,
    "status": "pending",
    "attached_at": "2026-01-10T10:00:00.000000Z"
  }
}
```

ID и дата здесь иллюстративные. `attached_at` — время создания привязки в ISO 8601 UTC. Признак `created` определяй по реальному результату записи (`wasRecentlyCreated`), а не предварительной проверке существования.

## GET /api/referrals/my

HTTP 200, объект `data` с массивом всех приглашённых текущим мастером, упорядоченных по ID привязки по возрастанию. Пагинация для этого задания не требуется.

```json
{
  "data": [
    {
      "id": 1,
      "master_id": 3,
      "name": "Ира",
      "attached_at": "2026-01-10T10:00:00.000000Z",
      "counted": true,
      "earned_amount": 30000
    }
  ]
}
```

`counted` соответствует `Referral::STATUS_REWARDED`. `earned_amount` — сумма сохранённых начислений по привязке, включая `pending` и `paid`, либо целочисленный ноль. Не пересчитывай награды из платежей или текущего процента. Используй eager loading/агрегацию, исключи запрос на каждую строку. Для отсутствующих приглашённых верни `{"data":[]}`.

## GET /api/referrals/earnings

HTTP 200, без обёртки `data`:

```json
{"total_accrued":30000,"pending":30000,"paid":0,"counted_referrals":1}
```

Все значения — JSON integers. Суммы получай из `referral_earnings` текущего реферера: общая, со статусом `pending` и со статусом `paid`. Количество — число его привязок со статусом `rewarded`. Пустая сводка содержит четыре нуля. Изоляция данных обязательна в обеих GET-выборках.

## Приёмка

Добавь feature-тесты успешных ответов, ошибок, повторной регистрации, отсутствующих данных и изоляции мастеров. Проверь даты, числовые типы, HTTP-коды и отсутствие новых начислений после POST. Для чистого seeder Маша получает 4 строки и сводку из примера; начисление есть только у Иры. Не добавляй маршруты создания платежей или выплаты наград.
