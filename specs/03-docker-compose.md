# 03. Воспроизводимый запуск через Docker Compose

## Цель

Запустить проект на машине с Docker и Compose без локальных PHP/Composer. Добавить отсутствующие Docker-файлы и согласовать инструкцию README с реально проверенными командами.

## Требуемая структура

- `Dockerfile`: PHP 8.3 FPM, Composer 2, расширения для Laravel, PDO SQLite и PHPUnit, определённые по `composer.lock`; многостадийная сборка зависимостей с dev-пакетами, поскольку нужны Scribe и тесты.
- `compose.yaml`: сервис `app` с PHP-FPM и сервис `nginx`. SQLite — единственная БД, Redis и отдельный сервер БД не нужны.
- `docker/nginx/default.conf`: document root `/var/www/html/public`, маршрутизация через `index.php`, FastCGI в `app:9000`. Не раздавать корень проекта.
- При необходимости `docker/entrypoint.sh` для инициализации зависимостей и прав; `.dockerignore` для исключения `.git`, `.env`, локальных `vendor`, БД, логов и кэша.

## Поведение окружения

1. Исходники монтируются в `/var/www/html`; правки PHP видны без пересборки. `vendor` хранится в именованном volume и инициализируется из собранного образа. Учитывай, что bind mount скрывает файлы образа.
2. Обеспечь обновление volume зависимостей при изменении `composer.lock` и пересборке: сравнение хэша и синхронизация либо другой явно описанный механизм. Не оставляй старый `vendor` незаметно.
3. Composer scripts запускаются только когда доступен `artisan` и нужные каталоги. Не требуется `.env` или рабочая БД для сборки образа.
4. PHP-процесс может писать в `storage`, `bootstrap/cache` и каталог SQLite. Не применяй рекурсивный `chmod 777` и не меняй владельца всего рабочего дерева. Объясни выбранное решение прав для Linux.
5. Публикуй Nginx на `127.0.0.1:${NGINX_PORT:-4400}:80`. PHP-FPM наружу не публикуй; убери неиспользуемый `PHP_FPM_PORT` из примера конфигурации.
6. В `.env.example` согласуй `APP_URL=http://localhost:4400` с портом; при смене `NGINX_PORT` пользователь должен также изменить `APP_URL`. Для локального запуска без Compose отдельно укажи порт 8000.
7. База `database/database.sqlite` сохраняется после `docker compose down` и повторного запуска. При старте контейнера не выполняй `migrate:fresh`, не перегенерируй ключ и не запускай seeder повторно.
8. Добавь проверку готовности HTTP через публичный `/api/ping`, используя реально установленную в образе утилиту. Настрой достаточный период ожидания старта.

## Документируемый первый запуск

Проверь и при необходимости уточни следующую последовательность:

```bash
cp -n .env.example .env
docker compose up --build -d
docker compose exec app php artisan key:generate
docker compose exec app sh -c 'test -f database/database.sqlite || touch database/database.sqlite'
docker compose exec app php artisan migrate --seed
curl http://localhost:4400/api/ping
```

Добавь команды логов, остановки, тестов и генерации документации. Явно пометь первоначальный seed как однократный. Команда сброса БД допускается только как отдельно подписанная операция для одноразовых данных.

## Приёмка

`docker compose config` валиден; сборка из чистого checkout проходит; сервисы запускаются; `/api/ping` и реферальная сводка доступны. После обычного перезапуска данные и `APP_KEY` сохранены. Изменение исходника видно без rebuild. `composer check-platform-reqs`, PHPUnit и `composer docs` выполняются внутри `app` (последние после соответствующих этапов). Секреты и локальная БД не попадают в образ или Git. Если Docker недоступен, зафиксируй непроверенные пункты, не заявляй успешный запуск.
